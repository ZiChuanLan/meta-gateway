# 计费

「计费」这一节讲的是：**一次请求应该记多少钱，以及它受哪些限额约束。**

## 两层单价链

单价按**整层替换**的优先级取，不是逐字段回退：

| 优先级 | 层 | 粒度 |
| --- | --- | --- |
| 1（最具体） | `route_members` 的单价列 | 该路由 × 该渠道 |
| 2 | `model_metadata` 的单价列 | 按模型名 |

**命中判定**：该层 `prompt > 0 || completion > 0 || per_request > 0 || 配了阶梯`，命中即停止下探。两层都没命中 → 成本记 0（免费）。

> [!WARNING]
> **层内不逐字段回退。** 只填了 completion 而 prompt 留 0 的那一层，prompt 会按 0 计（等于免费），**不会再去找下一层的 prompt 价**。这是「明明配了价却算出 0」最常见的原因。

## 成本公式

```
成本 = ( 输入/1000 × 单价prompt
       + 输出/1000 × 单价completion
       + 缓存读/1000 × 单价cache
       + 每次单价 )
     × 计费倍率 × 时段倍率
```

几个容易搞错的点：

| 项 | 行为 |
| --- | --- |
| **输入 token** | `prompt tokens + cache creation tokens`。缓存**写入**按 prompt 价计。 |
| **缓存读 token** | **不**计入输入量，单独按 cache 价计——它复用已经计过一次的上下文。 |
| **cache 单价为 0 时** | 回退到该层的 prompt 单价。 |
| **每次单价** | `per_request` 是第三层价格，适合「按次卖」的上游；走同一条两层链、乘同一个倍率。 |
| **倍率** | `model_ratios`，默认 `1.0`，范围 0~1000。**倍率不参与层选择**，只乘最后结果。 |

## 阶梯价与时段价

两层都可以各自带一套阶梯与时段表（存在该层的 JSON 列里）。

### 上下文长度阶梯

有些上游对长 prompt 收更贵的单价。阶梯是一串「档位」，每档有一个输入 token 上限：

| 字段 | 含义 |
| --- | --- |
| `max_prompt_tokens` | 该档覆盖的**上限**（含）。`0` 表示开放式，只能出现在最后一档，且最多一档 |
| `prompt` / `completion` / `cache` / `per_request` | 该档的四项单价 |

规则：

- 档位按上限排序，**请求落在哪一档就整档用那一档的价**（不是分段累进）。
- 选档用的是**输入 token 数**（prompt + cache creation），与计费口径一致，所以档位与账单不可能对不上。
- **请求超过所有显式上限时落到最后一档**，而不是计 0 —— 「比我们定过价的还多」的诚实答案是收最贵那档，免费等于白送。
- **配了阶梯时，阶梯压过扁平列**。一层的扁平列全 0 但配了阶梯，这一层仍然算「已定价」。
- 最多 20 档。

### 时段倍率

| 字段 | 含义 |
| --- | --- |
| `days` | ISO 星期号（1 = 周一 … 7 = 周日）；留空 = 每天 |
| `from_hour` / `to_hour` | 网关本地时区的小时（0–23）。结束不晚于开始 = **跨午夜**（22 → 6 覆盖 22、23、0…5）；两者相等 = 全天 |
| `multiplier` | 该时段内的倍率，必须 > 0 且 ≤ 1000 |

- **第一个匹配的时段生效**，不与后续时段相乘。重叠的时段拿到的是先写的那个，而不是一个叠乘出来的意外加价。
- 最多 20 个时段。
- 阶梯与时段**可以叠加**：夜间的一条长 prompt 先按档位定价，再乘时段倍率。

> [!NOTE]
> 畸形阶梯或时段表会被**记录并丢弃**，回退到扁平价，绝不让转发卡住。保存期校验才是挡住畸形值的第一道闸。

## 限额：token 与金额两套并行

产品里每个配额都曾只按 token 计，但对「买了 100 美元额度」的客户来说 token 是错的单位——同一个 token 在不同模型、不同渠道价格不同，token 预算表达不了花钱预算。所以现在有两套：

| 单位 | 列 | 位置 |
| --- | --- | --- |
| token 数 | `quota_total_tokens` / `quota_used_tokens` | 下游令牌、令牌分组、团队账户 |
| 金额 | `quota_total_cost` / `quota_used_cost` | 下游令牌、令牌分组、团队账户 |

**两者同时生效，谁先耗尽谁拒绝请求**，不是二选一。金额用账本本身的计价单位存储，切换显示币种不会改写历史。

> [!IMPORTANT]
> **配额与计价正交。** 配额按 token 数扣减，与单价无关；单价只影响 `usage_records.cost`。把单价设成 0 **不会**让配额免扣。

## 成本从哪读

展示的成本一律读真实账单，不做客户端估算：

| 位置 | 数据源 |
| --- | --- |
| Keys 页 cost 列 | `UsageStore.CostByKey()`（按 key 求和） |
| Logs 页 cost 列 | 按 `request_id` join `usage_records.cost`（`CostByRequestIDs`） |

日志行的 `Cost` 字段只在管理列表里填充，它不是成本的权威来源。

## 币种与显示

显示币种由 `currency_symbol` / `currency_rate` 控制，是**展示层**的事：改它不会重写任何历史成本。

## 额度码

团队额度码可以携带 token 额度，也可以携带金额额度（`team_invites.quota_cost`）。同一账号重复兑同一个码由唯一索引拦住；码的总次数由 `used_count < max_uses` 拦住。两者在同一个事务里先过再入账。
