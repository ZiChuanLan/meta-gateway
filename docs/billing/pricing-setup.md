# 定价配置

[计费](/billing/) 讲的是**规则**（怎么算）。这一页讲**在哪里填、以及那些填空框时最容易出错的地方**。

## 一、三个定价面

| 面 | 存储位置 | 粒度 | 优先级 |
| :--- | :--- | :--- | :--- |
| **路由成员单价** | `route_members` | 该路由 × 该渠道 | 1（最具体） |
| **模型单价** | `model_metadata` | 按模型名 | 2 |
| **计费倍率** | `model_ratios` | 按模型名 | 最后相乘，**不参与层选择** |

控制台里的定价面板把顺序写在界面上（成员价 → 模型价 → 倍率），因为「这个数字为什么是这个数」是操作员最难回答的问题。

## 二、每项在哪改

| 要改什么 | 去哪里 |
| :--- | :--- |
| 某个模型在某条路由某个渠道上的价 | 模型页 → 路由成员抽屉 |
| 某个模型的通用价 | 模型页 → 模型元数据 |
| 计费倍率 | 定价面板（`/admin/ratios`） |
| 用站点公开价回填成员价 | 站点探针对话框 → 「采用价格」 |

**两个抽屉共用同一个价格编辑组件**，所以四项扁平价、上下文阶梯、时段倍率在哪都长得一样：

| 字段 | 含义 |
| :--- | :--- |
| `price_prompt_per_1k` | 输入（每 1K token） |
| `price_completion_per_1k` | 输出（每 1K token） |
| `price_cache_per_1k` | 缓存读（每 1K token）；为 0 时回退到输入价 |
| `price_per_request` | 按次单价 |
| `price_tiers` | 上下文长度阶梯 |
| `price_schedule` | 时段倍率 |

## 三、`0` 与「空白」不是一回事

这是定价里最容易出错的一处，三处行为各不相同：

| 你做的事 | 结果 |
| :--- | :--- |
| **留空** 一个扁平价字段 | 该字段为 0。若整层都空 → 该层**不算已定价**，继续下探下一层 |
| **显式填 `0`** 在档位里 | **保留**：这一档就是 0（免费） |
| **清空**一个已有档位的价格字段 | **保存被阻止**，而不是把它变成免费 |

> [!WARNING]
> **清空档位价会阻止保存**，这是刻意的。档位里的空字段如果按 0 存下去，等于把这一档变成免费——那从来不是操作员的本意。所以界面拒绝保存，要求你给一个明确的值。

## 四、保存安全的四条规则

价格编辑器的行为有几条被测试钉死的规则，都是为了让「打开抽屉看一眼」永远不会损坏数据：

1. **未编辑的旧值原样保留。** 打开一个带**无法解析**的历史 `price_tiers` 文本的抽屉、直接保存，存回去的是**原来那段文本**，不是被清空的 `""`。抽屉不会毁掉它读不懂的值。
2. **完全空白的新档位 / 新时段会被忽略。** 点了「添加档位」但一个字段都没填就保存 → 提交的是空值（等于没有阶梯），而不是一行全 0 的档位。
3. **显式填 0 会被保留。** 把新档位的每个字段都填 `0` 再保存 → 存下来就是一行全 0 的档位（这一档免费）。规则 2 与 3 的区别就是「碰过没有」。
4. **清空已有档位价则阻止保存**（见上）。

## 五、采用观察价的三条铁律

站点探针能读到站点自己公开的价格表，可以一键回填成员价。实现上（`RouteMemberStore.AdoptObservedPrices`）有三条铁律：

| 铁律 | 原因 |
| :--- | :--- |
| **只填空位**，手工价绝不被覆盖 | 这就是「采用」可以放心按下去的原因——连按两次是纯空操作 |
| **token 族与按次族互斥** | 一半 token 一半按次的成员会把一次请求计成两个模式之和 |
| **族内整体填** | 有 prompt 无 completion 的半填行会把 completion 计成免费 |

另外，**报价不来自请求**：服务端从该成员所属行的最新采集样本取价，客户端**传不进数字**。

目录标准价（来自外部模型目录）**只展示、不提供采用**——它本来就是计费的第二层回退，再写进成员价只是复制一份会漂移的副本。

## 六、给一个新模型定价的完整流程

1. **先确认它是否已经有价。** 模型元数据可能已经从外部目录同步到了标准价——那是第二层，通常够用。
2. **需要渠道级差异时**才配成员价。同一个模型在不同渠道成本不同时（例如一个走官方、一个走转售），这是唯一的正确位置。
3. **配倍率**只在你要对**全部客户**统一加价（或打折）时用。倍率是按模型名的，不区分渠道。
4. **长 prompt 更贵的上游**用阶梯，不要用倍率近似——阶梯是按请求的输入量选的，倍率是全局乘数。
5. **夜间便宜的上游**用时段倍率，注意**第一个匹配的时段生效**，重叠时段不会相乘。
6. **验证**：发一次真实请求，然后在日志页看该行的 cost，与手算结果对一下。

## 七、常见错误

| 现象 | 原因 |
| :--- | :--- |
| 明明配了价，成本却是 0 | 只填了 completion 而 prompt 留 0：**层内不逐字段回退**，这一层的 prompt 按 0 计。要么把这一层填全，要么清掉这一层让它下探 |
| 只配了阶梯，成本却是 0 | 不应该——只配阶梯的层也算「已定价」。如果真的是 0，检查阶梯 JSON 是否畸形（畸形值会被丢弃并回退到扁平价） |
| 档位选错了 | 选档用的是**输入 token 数**（prompt + 缓存**写入**），缓存**读**不计入。这跟计费口径是同一个量，所以对不上就是别的地方错了 |
| 超过所有上限的请求算成了 0 | 不应该——超过所有显式上限时落到**最后一档**（最贵那档），不是免费 |
| 改了币种符号，历史成本变了 | 不应该——币种是**展示层**的，改它不重写任何历史成本 |
| 倍率改了，某个模型没变 | 检查该模型是否有倍率行；没有则默认 1.0 |
