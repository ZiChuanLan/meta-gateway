# 价格架构审查与分离方案

审查基线：`experiment/availability`，`28913cfb4c04f2eb33d776bcb4452b9f3fbc8b19`。本轮主代理独立完成；没有使用子代理，没有修改业务代码。本文是方案，不是已实现的功能。

## 结论

不要把所有站点都强行折成一个 USD 单价。应统一的是**数据契约、单位、适用范围、计算状态与证据**，不是假装不同站点的钱、账户、计费方式天然等价。

分开五件事：

1. **参考报价**：外部模型目录/第三方目录说什么，仅供参考。
2. **上游扣费规则**：这个站点、账户/Key 分组、真实模型究竟扣多少原生额度。
3. **实际支出或成本估计**：充值、赠送、兑换比例影响你实际上花多少钱；不等于站点显示的美元。
4. **网关计费规则**：本网关对下游请求记多少金额、扣哪些配额。
5. **余额估算**：在明确工作负载与约束下还能承担多少调用；不是账户原始事实。

观察可以自动刷新；自动观察不应偷偷改价。网关计费不在请求路径上依赖外部目录网络。

## 1. 修正前一轮报告

- `quota_per_unit == 500000` **不能证明任意 fork 的额度就是美元**。须由具体协议契约及来源证据判定，不按数字猜。
- New-API 官方源码中的美元基准，与某个商业站点的“美元额度”和你的真实充值支出不是同一个概念。保持原生额度仍可计算站内预算，不必先换成 USD。
- “只填 0”不等于保护人工设置：0 可能是免费，整层的字段可能来自多个来源，阶梯还可能覆盖平铺值。
- 缓存读报价缺失意味着“无法准确复制站点扣费”；不能仅凭此断言运营者自己的收费价非法。另有已复现的**缓存 token 重复计费**，见下一节。
- 按 token + 每请求附加费可以是合法的混合计费。要禁止的是“采纳固定价时意外混入原 token 价”，不是取消现有显式混合定价。
- 无法从源码证明“多数中文站”等市场覆盖比例。本报告只说明满足对应响应条件的站点。
- **两个目录不同**：`siteprobe/catalog.go:13-16` 导入监测源地址；`siteprobe/external.go:37-57` 只读第三方健康数据，未读价格。LiteLLM/models.dev 是 `modelcatalog` 的模型参考目录，不可混称一个“外部目录”。
- `channels.group_name` 在账号同步路径确实由上游 token group 填入（`account/service.go:1049-1162`），但不能把所有手工渠道分组都当作已验证的 Key 分组。必须区分上游计费组、网关路由成员组、下游配额组。

### 源码已确认的其他风险

- `siteprobe/newapi.go:146-161` 用显示币种覆盖数值币种，未应用显示汇率。本地 New-API mock 返回 CNY 展示、汇率 7.3；界面把 2.5/10 显示为 ¥2.5/¥10，而不是该协议下对应的人民币显示额。
- `adapters/account.go:213-224` 无 default 时取 map 首个正倍率。确定性与实际分组均不成立。
- New-API `controller/pricing.go:45-59` 会按登录用户重写 group_ratio；匿名/登录报价不同不一定是过期，而可能是两个有效的适用范围。不能合并成不带账户作用域的“唯一站点价”。
- ratio 分支没有 cache_ratio；`BillingCoefs.CacheWrite` 被解析但没进入 `PriceQuote`；直接报价中的 CacheWrite 同样丢失。
- `modelcatalog/service.go:474-489` 逐个填零，既不能区分人工免费，也无法刷新以前同步的非零旧价。
- `route.go:861-909` 先读后全行写，无版本条件；[INFERENCE] 并发人工改价可能被旧快照覆盖，需并发回归，不在本轮声称已复现。
- `siteprobe/match.go:117-118` 的 HasPrice 只看平铺列，漏阶梯；`CatalogPrices` 同样没有走完整层逻辑。按钮可显示“未设价”，实际上已有阶梯。
- `site_probe.go:149-199` 采纳请求只携带 member_ids，没有用户看到的 quote_id/revision；[INFERENCE] 查看与提交之间刷新会应用另一个报价。不能把这个风险当已经发生过的事故。
- `account/service.go:680-689` 缺失 quota 被填成 0，再可能发送低余额通知；“不可读”被当“欠费”。
- `FinanceOverview` 按渠道而非账户去重，每个渠道读取 self/pricing/status；共享账号多条渠道可能重复 IO。缓存 2 分钟、并发 4、总体超时 90 秒，页面读在 miss 时等待上游。应拆成后台快照读取和显式刷新。
- `routingPolicy.tsx:175-185` token 预算按输入价除余额并在百万单位上 floor；不足 1M 时即显示 0M，输出、缓存、阶梯、共享消费都没有进入假设。
- `proxy_health.go:365-375` 结束时读当前规则与当前时间；`store/usage.go:40-57` 只存费用/用量，没有价目版本。历史金额稳定，不代表可以解释当时为何这么算。
- `httpapi/relay.go:1083-1093` 中断流会按发送字节/4估 token，但持久层没记录 estimated 来源。估算不能伪装成上游精确回报。

## 3. 目标结构：三类规则，两个计算出口

```text
LiteLLM / models.dev ──────────────> 参考报价快照
监测目录 ─────> 观测源地址 / 第三方健康数据（与价格隔离）
上游公开价 / 登录价 ────────────────> 上游报价快照（带账号与分组作用域）
管理员手填上游报价 ────────────────> 上游人工覆盖
                                         │
                              上游扣费评估 / 余额估算
                                         │
                           显式“复制为网关计费规则”
                                         ▼
管理员网关定价 ──────────────────> 本地生效计费规则 + 版本
                                         │
                                      网关结算
                                         ▼
                                账单金额 + 结算证据
```

### 来源与用途是两个维度

“手动、站点、目录”回答来源；“参考、上游成本、网关收费”回答用途。不要再用单个 `price_source` 同时表达这两维。

手工上游价属于“上游扣费覆盖”，手工网关价属于“本地计费”，二者入口和保存目标不同。复制报价只产生一次本地版本，不隐含永久跟随。

### 最小落地边界

- 原有适配器负责 Fetch + Parse，报价格式解析不接触 usage ledger。
- 引入一个明确的 pricing 领域模块，集中单位校验、规则解析、上下文匹配、报价评估和状态生成；避免 siteprobe/account/frontend 三处计算。
- siteprobe 消费报价服务作为观察数据，不拥有计费写权限。
- account 保持账户/Key 余额、作用域和时间；价格从统一报价仓储读取，但按账户隔离缓存。
- billing 调用本地纯计算器；参考价 API、计费预览共享该计算器，不复制优先级规则。
- 不建微服务，不做任意语言表达式沙箱，不为了可能的需求铺大量抽象层。

## 4. 数据契约

### 4.1 MoneyUnit：不要只留一个符号

最少区分：

- `iso_currency`：有明确契约的 USD/CNY 等。
- `site_credit`：站内额度，ID 必须含 site identity，例如 `credit:site/12`；两站都叫 `$` 仍不能相加。
- `quota_point`：适配器原始计量整数，保留 quota_per_unit 等换算证据。
- `unknown`：值可展示原文，不做跨单位比较或采纳。

三种比例单独保存与命名：

1. **协议换算**：quota point → 站内计价单位。
2. **显示换算**：例如 New-API 把其基准额度乘 7.3 显示成人民币；仅决定展示。
3. **实际成本换算**：你充值多少真钱换多少额度，含折扣/赠送；可由操作员声明，带日期和来源，不从符号或通用汇率推断。

例：两站都显示 `$10`，一站充值 10 USD 获得，另一站活动充值 10 CNY 获得。这是两种不同采购成本；没有充值依据就只报告“站内余额”。

初期保持现有网关 USD 账本，不扩成多币种会计系统。站点原生币种与网关显示币种不能共用一个全局汇率。

### 4.2 QuoteSnapshot

建议字段：`id/revision/source_kind/source_ref/site_id/account_ref/upstream_group/upstream_model/endpoint/meter/unit/rates/conditions/observed_at/fetched_at/expires_at/parse_status`。

- 公开价与账号价分别存；upstream_group 不拿 route_members.group_name 顶替。
- 保留原始比率/表达式与适配器版本，便于复算；只保存价格允许字段，不能保存 Cookie/Authorization/账号私密响应。
- 同名模型必须有提供商/上游命名空间；不能只凭模糊名称把不同套餐合在一起。
- 报价完整性、是否新鲜、是否适用、能否计算是独立状态。`fetched_at` 是刚下载，不代表 `observed_at` 很新。
- 出错保留上次成功快照并显示刷新失败；新快照缺字段不是免费，更不是自动清空人工规则。

### 4.3 RateCard：明确零值与继承

规则状态：`inherit / explicit / free / legacy`。

规则内字段用 nullable 或显式 presence 区分：缺失、不适用、明确 0。不能继续用 `>0` 判断是否有完整价格。`free` 整层应压过 fallback；否则“设为免费”会被目录价重新覆盖。

计量模式为受控联合类型：

- `token`：普通输入、输出、缓存读、缓存写可独立定价。
- `request`：固定请求费。
- `hybrid`：明确允许 token + request fee，UI 必须显示为附加费。
- `unsupported`：图像分辨率、音频/秒、视频等超出现有计算器时保存原文与原因，不硬挤成 token 价。

上下文阶梯需要声明选档维度：总上下文、普通输入、输入含缓存等。缓存语义按协议归一化成互斥桶，避免重复扣费；保持原始 usage 计数用于展示，不能悄悄改变 token 配额口径。

金额精度：在新计算边界统一十进制定价、舍入点与账本精度；不在 UI 逐项 round 再汇总。旧 float 账本迁移先做影子比对，不直接重算历史。

### 4.4 BillingDecision

账单至少能回答：哪条规则/版本、哪一层、适用模型、真实承接 member、计量模式、用量来源、阶梯、倍率、时区/选时、计算状态。

建议请求接纳或具体 attempt 确定时冻结规则版本；fallback 改选上游时，上游成本规则随 attempt 选择，网关收费政策是否变价必须明确。先维持现有成员覆盖语义迁移，不能升级时让所有人收费变化。

新规则采用确定的生效时间/时区契约；旧规则保留“请求结束时计费”的 legacy 标记直至管理员修改。没有证据不要补造旧账单来源。

状态至少包括 `settled / explicitly_free / unpriced / usage_missing / estimated / calculation_error`。它们不能全化成 cost=0。

## 5. 余额与剩余调用：先算站内，不强求换汇

余额对象先区分 `account / credential / subscription / gateway_user`，标注总额、可用额、无限、到期、周期与共享范围。账户余额不是每个模型独立一份；同账号多渠道不重复加总。

- 按次：同一额度单位、明确价格与适用组时 `floor(available / fee)`；还需受 key 配额、到期和授权约束。
- 按量：默认不要在成员行常驻 `≈10M`。展示“余额 + 原生单位”，详细估算器要求普通输入/输出/缓存构成。
- 预计每次花费 = 选定工作负载各互斥桶的费用 + 固定费，再应用明确倍率。
- 预计次数 = 可用额度 / 预计单次额度；标“按该场景测算”，不是承诺。
- 只有输入上限估计时明确写“纯普通输入、不含输出的理论值”；不足 1M 显示 240k，不提前 floor 为 0M。
- 复杂表达式未支持、分组未知、币种不相容、额度陈旧时返回具体 `unavailable_reason`；不要显示 0。
- 价格为 0 不代表“无限调用”：仍有速率、token、时间、服务可用性限制。
- 如需“按近期请求估计”，仅在样本足够、同一账户/模型/条件下使用真实扣费或当前规则重估；余额差分会混入充值与站外消费，不是精确成本。

## 6. 使用流程

1. 新站点自动抓取支持协议，展示原生额度与报价来源。普通站点无需逐字段问答。
2. 仅在语义不足时出现局部“补充计价单位/分组”入口；未知不阻止健康观察与模型使用。
3. 网关价格默认在模型的计费面板管理；成员覆盖仅针对必要差异，清楚显示影响范围。
4. 点击“复制报价为网关价”打开一个紧凑差异面板：当前/目标、单位、作用对象、来源时间；一次提交，不串联多个确认向导。
5. 提交携带 quote revision + rule version，以事务/CAS 保证看到的就是写入的。规则已变化则提示重新比较，不能覆盖新值。
6. 报价刷新展示变化但不自动改账；未来如要自动跟价，须是另一个明确的订阅策略，限制来源与范围，不靠空值判断隐式启用。
7. 日志和账单入口解释金额，区分网关记账、上游估算；没有实际上游结算数据不标“利润”。

## 7. 兼容迁移与实施顺序

### A. 先补真实路径守卫

修复六个已复现缺陷；补 OpenAI/Anthropic/Gemini usage 桶、cache creation、免费价、仅缓存用量、无 usage 按次入账、中断流估算标记。验证真实 handler → RecordUsage，而非仅测计算函数。

### B. 让当前数据先可解释

新增报价作用域与单位/状态；独立 catalog reference 存储；拆显示货币与原生单位；停止新的隐式逐零填价。已存在计费列不清空、不推断来源，迁为 `legacy`。

### C. 建显式计费规则和解释出口

保留两层优先顺序但改为显式配置态；引入规则 revision/计算状态/快照；报价采纳原子化。旧规则结果与新 legacy evaluator 做样本对照。

### D. 最后换掉误导性的估算和价格 UI

统一 /1M 展示及编辑入口（旧 /1k 存储可在边界换算，暂不全库搬单位）；原生余额替代裸 M；模型计费、站点报价、目录参考分区展示。

### 关键验收

- 采集失败不改变生效收费；价格来源切换不改变已入账历史。
- 0/unknown/inherit 分别测试；免费缓存不回退输入价。
- 同模型不同账号/组不同价不会串缓存；默认组不存在不随机选。
- 无法解析或不适用报价不能伪装精确值；不能假定 symbol 相同即可比较。
- 复制报价模式切换双方方向、阶梯覆盖、版本冲突、部分失败均可解释。
- 估算范围不超过已知最紧账户/Key 约束，未知范围不装作已知。
